# Face API Modularization Spec

## The pain
当前 `face_api` 已经具备检测、比对、搜索、注册、轻量认证等能力，但它还更像一个“通用识别 demo API”，而不是一个能稳定复用到多个终端项目中的模块化能力服务。

当前具体痛点有两类：

1. **重复接入成本高**
   - 不同项目如果要接人脸能力，往往需要自己重新拼一套“检测 → 提 embedding → 判断单人脸/多人脸/无人脸 → 业务分流”的逻辑。
   - `electron-wms` 当前真实落地链路已经说明：业务真正高频复用的不是完整登录接口，而是“稳定提特征 + 稳定失败语义 + 稳定状态接口”。

2. **当前接口产品语义偏弱**
   - 现在缺少一个明确的原子接口用于“只提取单人脸 embedding 并返回稳定状态”。
   - 错误主要靠 `{ detail: ... }`，不利于前端和桌面端做稳定分流。
   - `/auth/face-login` 偏成品业务接口，但真正的复用场景并不总是想直接拿“登录结果”，而是要拿“识别证据”。

一个已发生且能说明问题的实例是：`electron-wms` 的真实登录主链路并没有直接依赖 Python 服务完成匹配和认证，而是只依赖本地 `/extract/base64` 类能力，再由 Electron 侧自己做本地 1:N 匹配、阈值判断、审计和离线回退。说明当前最应被复用的能力，是识别原子接口，而不是完整业务登录流程。

## The wedge (this spec)
第一阶段只解决一个最窄但最有杠杆的楔子：

> 把 `face_api` 改造成一个可复用的“统一识别原子接口服务”，让不同终端/桌面/业务系统都能稳定调用它完成检测、提 embedding、判断单人脸/多人脸/无人脸，并基于稳定错误码和状态语义做自己的业务编排。

本 spec 只覆盖以下内容：

1. 新增统一原子接口 `/extract/base64`
2. 为识别相关失败补充稳定的机器可读错误码 `code`
3. 增加一个更适合运维和集成方读取的 `/system/status` 接口
4. 重新明确接口分层边界：
   - runtime primitive
   - library helper
   - auth helper
   - ops helper（后续能力，不在本阶段全做）

本阶段明确不做：

- 不把 `face_api` 直接做成完整登录平台
- 不做离线权限治理
- 不做集中化审计平台
- 不做多终端管理看板
- 不做活体检测
- 不做大规模底库同步平台化
- 不强行把 `electron-wms` 的全部本地业务逻辑搬进 `face_api`

## Hidden capability (future, not this spec)
更长远的目标不是“一个人脸 API”，而是一个**可插拔终端能力模块体系**，其中人脸只是第一块能力。未来这个体系可以继续长出扫码、设备健康、门禁、工牌、离线认证辅助等模块。为此，`face_api` 需要从一开始就把接口边界、错误码、状态语义和运维端点设计清楚，作为后续模块扩展的样板，而不是继续堆叠成一个语义模糊的单体识别服务。

## Approach chosen
选择方案：**模块化能力层（单服务内分层，而不是一步拆成多个服务）**。

对外能力分层如下：

1. **runtime primitives**
   - `/health`
   - `/system/status`
   - `/extract/base64`

2. **library helpers**
   - 现有 `/faces/*`
   - 现有 `/search`
   - 后续可以再补状态型人脸库能力

3. **auth helpers**
   - 保留 `/auth/face-login`
   - 但明确它只是“识别后判定辅助”，不是完整业务登录系统

4. **ops helpers**
   - 本阶段只做 `/system/status`
   - 审计、汇总、配置查看作为后续阶段能力

选择这个方案而不是“只做最小原子接口层”或“直接做完整平台”的原因：

- 比纯最小方案更有前瞻性，能把模块边界先立住。
- 比完整平台方案更克制，避免第一阶段过度平台化。
- 最符合当前真实需求：先解决跨项目复用问题，再逐步把通用能力抽上来。

## Premises (locked)
1. **识别服务不等于业务登录服务**
   - 锁定：`face_api` 返回识别证据或辅助判定结果，不负责正式业务 token / session 签发。

2. **可复用的关键不是接口多，而是接口语义稳定**
   - 锁定：优先建设稳定的状态语义、错误码和原子接口，而不是优先扩接口数量。

3. **WMS 里的所有逻辑不应该原样搬进 `face_api`**
   - 锁定：只抽取跨项目通用的能力；终端特有的在线/离线编排、权限边界、业务状态流转仍保留在业务系统侧。

4. **第一阶段不做重平台化**
   - 锁定：先把可复用识别原子层收稳，再考虑 library / auth-helper / ops 的增强。

## Out of scope
以下内容明确不属于本次 spec：

- 完整的人脸登录平台
- 业务 token、session、RBAC 或业务权限判定
- 离线登录有效期和补偿同步机制
- 多终端集中化审计看板
- 活体检测 / 防照片攻击
- 批量同步用户头像与人脸底库的通用平台化
- 人脸库质量治理平台
- 把 WMS 的 Electron 本地 SQLite 结构直接搬进 `face_api`

## Open questions
1. `/extract/base64` 的成功返回是否需要同时返回：
   - `embedding`
   - `face.bbox`
   - `face.det_score`
   - `landmarks`
   - `quality hints`（后续）

2. 错误码设计是否采用：
   - HTTP 状态码 + JSON `code`
   - 还是统一 200 包业务码（当前倾向前者）

3. `/auth/face-login` 是否保持当前接口名和大致行为不变，仅增强失败响应；还是后续降级为 helper 型接口并弱化其“完整登录”暗示。

4. `/system/status` 的粒度是否只到：
   - provider / device / model / det_size / db_count / auth_enabled
   还是还要暴露更多运行时检查项。

5. 本阶段是否只新增 `/extract/base64` 而不调整现有 `/detect/base64` 语义；当前倾向保留 `/detect/base64` 用于“展示型检测”，新增 `/extract/base64` 用于“业务型识别原子接口”。
