# V2.5 通用接入契约与服务化基线设计

> 日期：2026-06-19
> 状态：已确认设计，已完成 spec-kit 实施
> 范围：文档与契约基线，不改公开 API，不改运行时代码

## 1. 背景

V2.3 已完成 `face_api` 自身的固定摄像头现场验收，V2.4 已澄清 WMS 当前仍是内置人脸识别算法直接登录，尚未接入 `face_api` REST API。

新的产品判断是：`face_api` 后续不只服务 WMS，而是要作为多个项目可复用的本地或边缘人脸识别 REST API 服务。因此 V2.5 不应该直接写 WMS adapter，也不应该过早做 SDK 或多租户平台，而是先把通用接入契约、服务边界、运行方式和验收标准统一下来。

## 2. 设计原则

- API-first：所有接入方先遵守同一 REST 契约，再决定自己是 Java、Electron、Web 还是终端。
- 业务边界清晰：`face_api` 只返回识别、活体、风险、audit 和运行状态，不签发业务 session/JWT/SSO。
- 简单优先：V2.5 不新增公开 API、不新增数据库表、不引入 SDK、不改算法。
- 可验证：完成标准不是“文档写了”，而是新接入方能按文档完成最小联调路径。

## 3. 推荐接入模式

### 3.1 业务后端代理模式

普通 Web 项目默认使用这个模式。浏览器只持有业务系统自己的登录态，不保存、不展示、不打印 `X-API-Key`。Java / Spring Boot 或其他业务后端保存 `FACE_API_KEY`，代理调用 `/liveness/challenges`、`/liveness/challenges/submit`、`/auth/face-login`、`/faces/register` 等接口。

登录成功后，业务后端使用 `match.user_id` 或 `match.username` 查询自己的用户表，再签发自己的 session/JWT/SSO。

### 3.2 受控终端直连模式

Electron、一体机、闸机、Windows 客户端等受控设备可以直连 `face_api`，但必须满足：

- 设备由项目方管理。
- 可以安全配置 `X-API-Key`。
- 使用稳定 `terminal_id`。
- 失败结果能进入终端日志或业务后端 audit。

WMS 未来接入时应作为这个模式的一个具体消费者，而不是让 `face_api` 为 WMS 单独长出专用接口。

### 3.3 本地运维验收模式

`admin.html`、`camera-integration.html`、`acceptance.html` 用于本机调试、运维验收和现场排障。它们可以填写 API Key，但不代表正式互联网业务前端可以持有 API Key。

## 4. 标准数据流

### 4.1 Web 业务登录

```text
浏览器摄像头
-> 业务后端
-> Face API liveness challenge
-> Face API face-login
-> 业务后端查用户表
-> 业务后端签发 session/JWT
-> 浏览器进入业务系统
```

### 4.2 受控终端登录

```text
受控终端摄像头
-> Face API liveness challenge
-> Face API face-login
-> 终端拿到 match
-> 业务后端校验用户状态
-> 业务系统完成登录或放行
```

### 4.3 运行排障

```text
GET /health
-> GET /system/status
-> GET /config/effective
-> GET /audit/login/recent
-> 日志和备份恢复 runbook
```

## 5. 错误处理契约

接入方必须以 `detail.code` 作为稳定分支依据，以 `detail.message` 和 `detail.reason` 作为中文提示和排障说明。

关键规则：

- `AUTH_INVALID_OR_MISSING`：先检查 `FACE_API_KEY` 与请求头 `X-API-Key`。
- `NO_FACE` / `MULTIPLE_FACES`：提示用户调整摄像头画面。
- `LIVENESS_CHALLENGE_REQUIRED` / `LIVENESS_CHALLENGE_INVALID`：重新创建并提交 challenge。
- `ANTI_SPOOF_MEDIUM_RETRY_REQUIRED`：保存 `detail.retry.risk_retry_token`，重新采集一次并回传 token。
- `ANTI_SPOOF_MEDIUM_RETRY_EXHAUSTED` / `ANTI_SPOOF_HIGH_RISK`：本次失败，转人工或业务失败处理。
- `NO_MATCH`：用户未注册、阈值过高或现场图片质量不达标。

## 6. V2.5 明确不做

- 不新增公开 API。
- 不新增环境变量。
- 不新增数据库表。
- 不新增 JavaScript/Java SDK。
- 不修改 WMS 代码。
- 不修改算法阈值。
- 不引入 `app_id`、`client_id`、namespace 的真实实现。
- 不做中心管理平台、多租户、配额或统一账号体系。

## 7. 后续演进

短期：

- 一个项目一个 Face API 实例。
- 通过统一接入契约减少重复解释和联调误差。

中期：

- 如果多个项目共用一个实例，再评估 `app_id`、`client_id`、namespace、项目级 audit。

长期：

- 如果外部客户规模扩大，再评估中心化管理、多项目配额、统一审计和 SDK。

## 8. 成功标准

V2.5 完成后，新接入方应能回答：

- 我应该使用业务后端代理、受控终端直连，还是本地运维验收模式？
- `X-API-Key` 放在哪里？
- 浏览器能不能直接调用？
- Java / Spring Boot 怎么代理？
- Electron / 终端怎么直连？
- 登录失败时看哪个错误码？
- 中风险重试怎么处理？
- audit 怎么查？
- Windows 工作站怎么启动、停止和监控？
- CPU/GPU 怎么切换？
- WMS 后续接入应该按哪条标准路径推进？
