# Face API 与 WMS 智能抓拍联动闭环设计

> 日期：2026-06-17
> 状态：设计稿已确认，等待实施计划
> 适用项目：
> - `H:\AI_test\face_api`
> - `H:\AI_test\electron-wms\electron-wms`

## 1. 目标

把 `face_api` 的算法底座和 Electron WMS 的智能抓拍、终端登录、现场采集能力串成一条可反复执行、可验收、可复盘的 PDCA/trace 流程。

这条流程不把两个项目割裂成“算法项目”和“业务项目”，而是按真实现场链路管理：

```text
业务场景定义
-> Face API 能力确认
-> WMS 终端采集与调用
-> 现场样例验收
-> 审计与日志回收
-> 问题分类
-> 下一轮算法和终端改进
```

## 2. 当前上下文

`face_api` 当前定位是本地 Windows 工作站上的人脸识别 REST API，已具备检测、特征提取、比对、搜索、人脸库、登录辅助、轻量活体、防翻拍风险治理、审计和验收页面能力。V2.3 的重点是轻量防翻拍阈值治理与中风险重试机制。

Electron WMS 当前定位是智能仓储终端应用，包含用户同步、本地人脸库构建、摄像头采集、视频录制、终端人脸登录、离线回退、登录审计和现场运维能力。它承担真实业务场景和终端采集质量。

两者的关系应固定为：

| 层级 | 项目 | 职责 |
|---|---|---|
| 算法底座 | `face_api` | 识别、活体、防翻拍、错误码、审计、验收指标 |
| 终端业务 | `electron-wms` | 摄像头采集、抓拍/录制、业务登录、弱网回退、现场交互 |
| 联动闭环 | 两个项目共同 | 样例测试、问题归因、策略调参、下一轮改进 |

## 3. 设计原则

1. 先验收业务链路，再讨论局部优化。
2. 每次迭代必须留下输入、过程、输出和结论。
3. 问题必须归类到算法底座、终端采集、业务流程三类之一。
4. Face API 的接口语义和 WMS 的终端表现必须一起验收。
5. 自动测试只能证明基础不坏，现场样例才证明业务可用。
6. 不把 V2.3 扩展成重型强活体或完整风控平台。

## 4. 三条可复用 Trace

### 4.1 功能联动 Trace

用途：开发新能力或改造链路，例如抓拍后做人脸识别、抓拍质量判断、抓拍证据上传、登录失败提示优化。

输入：

- 业务目标
- 目标用户或终端角色
- Face API 涉及接口
- WMS 涉及页面、IPC、服务或摄像头链路
- 验收标准

步骤：

1. 明确业务场景和成功定义。
2. 列出 Face API 需要提供的能力、错误码、配置和审计字段。
3. 列出 WMS 需要采集、展示、调用和保存的数据。
4. 对齐接口契约和失败语义。
5. 实现或调整最小闭环。
6. 运行自动测试和手工链路测试。
7. 形成联动验收记录。

输出：

- 功能链路说明
- 接口与页面变更清单
- 测试命令和结果
- 现场操作步骤
- 下一轮改进项

### 4.2 现场验收 Trace

用途：跑真实样例，证明系统在现场环境下可用。

输入：

- Face API 版本
- WMS 版本
- 终端设备信息
- 摄像头型号或采集方式
- 光照、距离、角度等现场条件
- 样例集合

默认样例集合：

- 真人正脸
- 真人弱光
- 真人侧脸或轻微遮挡
- 打印照片
- 手机屏幕照片
- 电脑屏幕照片
- 手机播放眨眼视频
- 多人入镜
- 模糊抓拍

步骤：

1. 启动 Face API 并记录配置。
2. 启动 WMS 终端并确认摄像头权限、服务状态和本地人脸库状态。
3. 每类样例至少执行固定次数，保留结果。
4. 记录 Face API 返回的风险等级、错误码、相似度、耗时和审计字段。
5. 记录 WMS 端的提示、登录状态、离线回退和业务提交结果。
6. 将问题归类到算法底座、终端采集、业务流程。
7. 产出验收结论和下一轮调整建议。

输出：

- 联动验收记录
- 样例结果表
- 问题分类表
- 配置快照
- 下一轮版本建议

### 4.3 问题复盘 Trace

用途：处理现场反馈，例如识别慢、误识别、抓拍模糊、登录失败但原因不清楚、翻拍样例被放过。

输入：

- 用户反馈或现场现象
- 发生时间
- 终端编号
- Face API 审计记录
- WMS 日志或操作记录
- 可复现样例

步骤：

1. 用一句话定义问题。
2. 判断问题是否可复现。
3. 回收 Face API 审计、WMS 终端日志、配置和样例。
4. 归类根因：
   - 算法底座：检测、特征、相似度、风险评分、错误码、审计。
   - 终端采集：摄像头、光照、角度、模糊、权限、帧质量。
   - 业务流程：用户底图、账号状态、token 换取、离线回退、提示语。
5. 定义修复或调参方案。
6. 补充测试样例。
7. 更新下一轮 trace。

输出：

- 复盘结论
- 根因分类
- 修复建议
- 需要补充的自动测试或现场样例
- 是否进入下一版本 Roadmap

## 5. 数据流设计

标准联动数据流：

```text
WMS 摄像头采集
-> 截图/视频/连续帧
-> WMS 本地预检查
-> Face API 检测/活体/登录辅助
-> Face API 返回结构化结果
-> WMS 显示业务提示或发起登录
-> WMS 业务后端换取 token
-> Face API 与 WMS 分别写入审计/日志
-> 联动验收记录汇总
```

关键字段应被持续关注：

| 字段 | 来源 | 用途 |
|---|---|---|
| `terminal_id` | WMS | 区分现场终端和设备环境 |
| `event_id` | WMS 或业务链路 | 串联一次抓拍、识别、登录或提交 |
| `similarity` | Face API | 判断匹配可信度 |
| `risk_level` | Face API | 判断活体或翻拍风险 |
| `failure_reason` | Face API / WMS | 解释失败原因 |
| `elapsed_ms` | Face API / WMS | 判断性能瓶颈 |
| `face_login_threshold` | Face API / WMS 配置 | 复盘阈值影响 |
| `capture_quality` | WMS 后续可扩展 | 解释模糊、弱光和角度问题 |

## 6. 错误处理与归因规则

每个问题必须优先按下面规则归因：

| 现象 | 优先归因 |
|---|---|
| 无人脸、多人人脸、图片无法解码 | 终端采集或样例质量，必要时回查 Face API 检测 |
| 真人多次失败但图像清晰 | 算法底座阈值、底图质量或相似度策略 |
| 翻拍样例低风险通过 | Face API 防翻拍风险评分和中风险策略 |
| WMS 提示不清楚 | 业务流程和终端交互 |
| Face API 返回正确但 WMS 登录失败 | WMS token 换取、用户状态或后端认证链路 |
| WMS 端慢但 Face API 耗时正常 | 摄像头采集、前端处理或 Electron 主进程链路 |
| Face API 耗时高 | 模型、CPU/GPU、det_size、线程数或运行环境 |

归因不允许只写“算法问题”或“现场问题”。必须写清楚证据来自哪个日志、审计字段、样例或复现步骤。

## 7. 验收设计

一次联动验收至少包含：

1. Face API 健康检查。
2. WMS 终端启动和摄像头权限检查。
3. 本地人脸库状态检查。
4. 真人正脸样例。
5. 翻拍攻击样例。
6. 低质量采集样例。
7. 登录或业务提交链路。
8. 审计记录回收。
9. 问题分类。
10. 下一轮改进清单。

建议成功标准：

- 真人正脸 3 次至少 2 次成功。
- 打印照片、手机屏幕照片、电脑屏幕照片和播放视频不得低风险静默成功。
- 中风险必须进入重试、失败或复核语义，不能直接当作普通成功。
- WMS 端必须给出可理解的失败提示。
- 每次失败都能在 Face API 审计或 WMS 日志中找到对应记录。
- 验收结束后能明确问题属于算法底座、终端采集还是业务流程。

## 9. 下一步实施建议

第一轮实施不要直接写大功能，应先做“联动验收基线”：

1. 新建一份联动验收记录模板。
2. 用 Face API V2.3 和当前 WMS 终端跑一次完整链路。
3. 汇总样例结果和问题分类。
4. 决定下一轮优先改 Face API、WMS 采集，还是业务提示。

第一轮实施的目标不是把所有问题修完，而是建立一个以后每次都能复用的闭环。
