# face_api V1.8 现场交付与维护闭环设计

> 日期：2026-06-09  
> 状态：已按用户确认方向形成设计，待用户 review 后进入实施计划  
> 范围：V1.8 后续优化方向  

## 1. 背景

当前项目已经完成 V1.7.1 和 V1.7.2 的核心目标：

- Windows 工作站可以启动和长期运行。
- 默认 CPU 推理，必要时可通过配置切换 GPU。
- 摄像头注册、登录、活体、中文错误原因和最近 login audit 已形成现场闭环。
- `architecture.html` 已成为可交互的项目架构演示入口。
- 文档已按 PRD、季度计划、部署、使用、架构、性能等目录进行整理。

下一步继续优化时，主要风险不再是“少一个接口”，而是：

- 现场人员不会稳定启动、检查和排障。
- 新同事看到文档太多，不知道先看哪里。
- `main.py` 已经达到约 1800 行，后续继续加功能会降低可维护性。
- 架构图虽然可以演示，但还可以进一步服务培训、讲解和交付。

因此 V1.8 的主题建议定为：

> 把 face_api 从“功能可用”推进到“现场好交付、问题好排查、架构好讲解、代码好维护”。

## 2. 目标

V1.8 重点优化 5 个方向。

### 2.1 现场验收台

增强 `camera-integration.html` 或相关本地页面，使它更像现场验收工具，而不是普通调试页面。

目标能力：

- 检查 API 地址是否可访问。
- 检查 API Key 是否正确。
- 检查摄像头是否可用。
- 完成注册、登录、活体和最近 audit 闭环。
- 失败时展示中文错误原因和下一步处理建议。
- 明确提示正式生产不建议普通前端长期持有 `X-API-Key`。

### 2.2 运行状态总览

让小白也能一眼知道服务现在是否正常。

目标能力：

- 当前服务是否在线。
- 当前 CPU/GPU 推理模式。
- API Key 是否启用。
- 数据库路径和人脸数量。
- 日志路径。
- 端口占用和进程信息。
- 最近 login audit 成功/失败情况。
- 备份入口和最近备份状态。

该能力可以先放在本地 HTML 页面或 `admin.html` 中，不要求变成完整后台系统。

### 2.3 可维护性拆分

在保持接口行为不变的前提下，逐步降低 `main.py` 的复杂度。

建议优先拆分：

- 配置读取与启动校验。
- 结构化错误码和中文原因。
- Pydantic 请求/响应模型。
- login audit 读写与摘要。
- 活体 challenge 逻辑。
- admin/backup/maintenance 运维逻辑。

拆分原则：

- 不改变已有 API 路径。
- 不改变响应字段含义。
- 不改变数据库 schema，除非单独立项。
- 每次拆分都要有单元测试保护。
- 拆分后 `main.py` 继续保留 FastAPI app 入口和路由编排职责。

### 2.4 架构图演示增强

继续保持 `architecture.html` 为原生 HTML、CSS、JS 和 SVG 单文件，不引入框架和外部依赖。

建议增强：

- 演示模式：隐藏或弱化侧栏，让投屏时图谱更突出。
- 流程播放：注册、登录、搜索、运维、备份按步骤自动高亮。
- 讲解脚本：每个流程给出简短讲解词，方便给同事介绍。
- 导出截图：方便把当前架构状态发给同事或写进文档。
- 维护提示：页面内或文档中说明改接口、启动方式、存储结构时必须同步架构图。

### 2.5 文档与进度同步

当前文档体系已经比较完整，但需要把“已完成”和“下一步”同步干净。

目标能力：

- 季度计划中 V1.7 的状态与真实提交一致。
- 下一版本明确切换到 V1.8。
- superpowers 计划文档里的未勾选项不再误导用户。
- 文档入口说明“新同事、前端、运维、负责人”分别应该先看哪几份。
- 架构图和正式架构文档的关系保持清楚。

## 3. 非目标

V1.8 不建议做这些内容：

- 不做完整业务用户系统。
- 不签发 token、session 或权限。
- 不接管业务后端职责。
- 不引入 React、Vue、D3、ECharts 或在线 CDN。
- 不默认上 Faiss 或向量数据库。
- 不默认引入更强活体模型或硬件活体。
- 不把本地页面做成正式互联网管理后台。
- 不在没有性能证据前大改搜索架构。

## 4. 推荐实施顺序

### 阶段 1：文档与版本基线收口

先清理当前状态，让后续开发不跑偏。

交付物：

- 更新季度计划，把 V1.7.1 和 V1.7.2 标为已完成。
- 新增或更新 V1.8 路线说明。
- 清理已完成计划中的未勾选项，避免右侧进度误导。
- 明确 V1.8 的范围、非目标和验收标准。

### 阶段 2：可维护性拆分

在新增大功能前，先降低 `main.py` 继续膨胀的风险。

交付物：

- 提取配置、错误、schema、audit、liveness、admin ops 中最独立的一批模块。
- 保持所有接口行为不变。
- 单元测试全部通过。
- 架构文档同步说明模块边界。

### 阶段 3：现场验收台和状态总览

让现场人员能按页面完成检查和排障。

交付物：

- 页面提供启动前后检查清单。
- 页面能检查服务、API Key、摄像头、注册、登录、audit。
- 错误原因展示清楚。
- 运维状态显示更直观。

### 阶段 4：架构图演示增强

让架构图成为交付讲解工具。

交付物：

- 演示模式。
- 流程播放。
- 讲解脚本。
- 截图导出。
- 文档同步规则。

## 5. 验收标准

V1.8 可以认为完成，当满足：

- 新同事能从文档入口在 10 分钟内知道项目目标、启动方式、接口入口和架构入口。
- 现场人员能通过本地页面或脚本判断服务是否在线、API Key 是否正确、摄像头是否可用。
- 注册、登录、活体、中文错误原因和最近 audit 能在一个清晰流程中完成。
- `main.py` 的核心职责更清楚，后续新增功能不需要继续把所有逻辑塞入同一个文件。
- 架构图能用于投屏讲解，并能按流程说明系统工作方式。
- 所有现有单元测试通过。
- API 行为、启动脚本、数据库文件和文档入口保持一致。

## 6. 风险与约束

- 可维护性拆分属于高风险内部改造，必须小步提交，不应一次性重写。
- 页面增强不能泄露 `X-API-Key`、embedding 或敏感数据库内容。
- 现场验收页面可以直连 face_api，但正式业务前端仍建议通过业务后端代理。
- 架构图必须继续离线可用，不能依赖外部网络。
- 文档清理不能删除历史依据；已完成版本应归档或标注状态，而不是丢失上下文。

## 7. 后续计划入口

用户确认本设计后，下一步应进入实施计划阶段。

建议计划文件主题：

- `face_api V1.8 文档与版本基线收口计划`
- `face_api V1.8 main.py 可维护性拆分计划`
- `face_api V1.8 现场验收台与状态总览计划`
- `face_api V1.8 架构图演示增强计划`

实际实施时建议按阶段逐个执行，避免同时修改文档、路由、页面和模块边界造成回归风险。
