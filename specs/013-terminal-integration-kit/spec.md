# 功能规格：终端接入规范包

**功能分支**：`013-terminal-integration-kit`

**创建时间**：2026-06-05

**状态**：草案

**输入**：用户描述：“Roadmap v1.1 需要统一 terminal 和业务系统接入本地人脸识别 API 的方式。”

## Clarifications

### Session 2026-06-05

- Q: V1.1 是否强制每个 login 请求都带 `terminal_id`？ → A: 强制。
- Q: 业务系统和 face_api 的主接入方式是什么？ → A: 业务系统主动调用 face_api，face_api 只返回结果。
- Q: `terminal_id` 是否用于注册流程？ → A: 注册和 login 都必须传。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 业务开发者接入 face login（优先级：P1）

业务系统开发者需要清晰的主动调用流程：发送人脸图片、接收匹配到的业务用户身份，并处理失败情况。

**优先原因**：只有业务系统能可靠调用，本地人脸 API 才能真正产生价值。

**独立测试**：开发者按文档流程完成 face login 接入，不需要依赖未文档化行为。

**验收场景**：

1. **假如** 业务系统已获取人脸图片，**当** 按 login 接入流程主动调用 face_api，**那么** 可以收到匹配用户身份或清晰失败原因。
2. **假如** login 失败，**当** 业务系统映射失败 code，**那么** 用户或运维人员能看到正确处理建议。

---

### 用户故事 2 - 交付工程师一致识别 terminal（优先级：P1）

交付工程师需要每个 terminal 或客户端在请求、日志和 audit 中使用一致身份。

**优先原因**：多 terminal 现场问题如果无法区分来源，会很难排查。

**独立测试**：来自某个命名 terminal 的请求，在 audit 和诊断中显示同一个 terminal identity。

**验收场景**：

1. **假如** terminal 带着自身 identity 发送 login 请求，**当** 该尝试被 audit 记录，**那么** audit 中显示相同 terminal identity。
2. **假如** 某个 terminal 连续失败，**当** 运维人员按 terminal 过滤诊断，**那么** 只显示该 terminal 的尝试。
3. **假如** 注册请求缺少 `terminal_id`，**当** 请求进入注册流程，**那么** 服务拒绝请求并提示必须提供 terminal identity。

---

### 用户故事 3 - 业务开发者处理 retry 和 timeout（优先级：P2）

业务系统开发者需要 timeout、retry、重复提交和离线行为指导。

**优先原因**：错误 retry 会压垮工作站，或制造混乱的 login 尝试。

**独立测试**：开发者按文档配置客户端 timeout 和 retry，验证不会产生不受控重复请求。

**验收场景**：

1. **假如** 服务临时不可用，**当** 客户端按 retry 指引处理，**那么** 它返回受控失败，并避免无限重试。

### 边界情况

- terminal identity 缺失。
- terminal identity 异常变化。
- 业务系统在 timeout 前没有收到响应。
- 注册请求被重复提交。
- 业务系统和人脸 API 对 user_id 理解不一致。
- 业务系统误以为 face_api 会主动 callback。

## 需求 *(必填)*

### 功能需求

- **FR-001**：接入规范必须文档化注册、search 和 face login 的业务系统主动调用流程。
- **FR-002**：注册和 face login 请求必须强制携带 `terminal_id`。
- **FR-003**：接入规范必须定义 terminal identity 在请求、日志和 audit 中的使用方式。
- **FR-004**：face_api 不主动 callback 业务系统；业务系统必须主动调用并处理返回结果。
- **FR-005**：接入规范必须提供中文失败 code 映射指引。
- **FR-006**：接入规范必须定义客户端 timeout 和 retry 建议。
- **FR-007**：接入规范必须说明业务系统如何处理匹配返回的 `user_id` 和 `username`。
- **FR-008**：接入规范必须提供 terminal 上线前交付检查清单。
- **FR-009**：接入规范应该包含可运行或可复制的业务开发示例。

### 关键实体

- **terminal identity**：用于诊断请求来源的稳定标识，注册和 login 都必须提供。
- **接入流程**：业务客户端和人脸 API 之间的文档化调用顺序。
- **失败映射**：从识别失败到用户/运维动作的对应关系。
- **交付检查清单**：terminal 上线前需要验证的步骤。

## 成功标准 *(必填)*

### 可度量结果

- **SC-001**：在已准备好的环境中，业务开发者能在 30 分钟内完成文档化 face login 流程。
- **SC-002**：100% 文档化 terminal login 示例都包含 terminal identity。
- **SC-003**：常见失败 code 都映射到清晰的用户/运维动作。
- **SC-004**：交付检查清单覆盖注册、login、失败处理、audit 可见性和健康检查。
- **SC-005**：100% 缺少 `terminal_id` 的注册和 login 请求在契约测试中被拒绝。

## 假设

- 人脸 API 返回识别结果，业务系统做最终业务决策。
- terminal identity 是诊断和接入概念，不替代用户鉴权。
- V1.1 接入范围先面向局域网客户端，不做云同步。
- V1.1 主接入模式是业务系统主动调用 face_api，不采用 face_api 主动 callback。
