## 用户场景与测试

### 用户故事 1 - 验收人员能记录完整联动链路（P1）

验收人员需要一份 Face API 侧模板，按固定步骤记录 WMS 摄像头采集、Face API 识别结果、WMS 页面表现、audit、日志和问题归因。

**独立测试**：打开 Face API 联动验收模板，能从空白模板直接填写一次完整现场验收，且不需要阅读历史聊天记录。

**验收场景**：

1. **假如** Face API 和 WMS 都已启动，**当** 验收人员按模板执行真人正脸样例，**那么** 模板能记录配置快照、WMS 操作、Face API 风险等级、相似度、耗时和审计是否可查。
2. **假如** 翻拍或模糊样例失败，**当** 验收人员记录结果，**那么** 模板能把问题归到算法底座、终端采集或业务流程。

### 用户故事 2 - WMS 终端开发者能按 runbook 复现现场检查（P1）

WMS 终端开发者需要知道如何启动 WMS、确认摄像头权限、本地人脸库、Face API 连通性、页面提示和日志位置。

**独立测试**：只阅读 WMS runbook，开发者能完成一次摄像头登录或抓拍联调，并知道失败时收集哪些证据。

**验收场景**：

1. **假如** WMS 已安装依赖或已打包，**当** 开发者按 runbook 启动终端，**那么** 能确认摄像头权限、测试用户、人脸库状态和 Face API 连通性。
2. **假如** WMS 页面提示失败，**当** 开发者查 runbook，**那么** 能知道该看 WMS 日志、Face API audit、业务登录结果还是现场采集条件。

### 用户故事 3 - 项目负责人能用统一规则决定下一轮改哪里（P2）

项目负责人需要把现场问题按证据归类，避免所有问题都被口头归为“算法问题”或“现场问题”。

**独立测试**：使用问题分类表复盘一次失败样例，能明确下一轮进入 `face_api`、WMS 终端采集，还是业务提示/流程。

**验收场景**：

1. **假如** Face API 返回正确但 WMS 登录失败，**当** 负责人查看验收记录，**那么** 能归为业务流程或 WMS token/用户状态问题，而不是算法问题。
2. **假如** WMS 很慢但 Face API 耗时正常，**当** 负责人查看耗时和日志，**那么** 能归为终端采集或 Electron 链路问题。

### 用户故事 4 - 后续 `/goal` 能直接执行 V2.4（P2）

后续实施时需要一个清晰入口，能从 roadmap、spec、plan、tasks 和文档索引开始，不重新翻聊天记录。

**独立测试**：从 `specs/README.md` 和 `docs/02_product/02_quarterly_plan.md` 能找到 V2.4 执行入口、边界和验收标准。

## 边界情况

- WMS 仓库路径不存在：停止实施 WMS runbook 写入，记录阻塞，不猜测目录。
- WMS 工作区不干净：只读检查后提示，不覆盖用户未提交变更。
- Face API 服务未启动：模板应要求先完成 `/health` 和配置检查。
- 摄像头被占用或无权限：归入终端采集问题，并记录设备和权限状态。
- Face API 返回 401/403：优先检查 `FACE_API_KEY` 与 WMS 端 `X-API-Key`。
- 验收人员没有真实样例：不得把模板标记为已通过，只能标记为待执行。

## 功能需求

- **FR-001**：必须新增 V2.4 roadmap，说明版本定位、范围、不做事项和推荐 `/goal`。
- **FR-002**：必须新增 `025-wms-capture-loop-baseline` spec-kit 目录，包含 `spec.md`、`plan.md` 和 `tasks.md`。
- **FR-003**：必须新增 Face API 侧联动验收模板，覆盖环境快照、启动检查、样例矩阵、单次记录、问题分类、验收结论和下一轮改进。
- **FR-004**：必须新增 WMS 侧终端 runbook，覆盖启动前检查、摄像头检查、本地人脸库、Face API 调用、日志证据和归因规则。
- **FR-005**：验收模板必须明确不保存 API Key、原图、视频帧、连续帧、embedding 或用户敏感信息。
- **FR-006**：验收模板必须至少包含 9 类样例：真人正脸、真人弱光、真人侧脸或轻微遮挡、打印照片、手机屏幕照片、电脑屏幕照片、手机播放眨眼视频、多人入镜、模糊抓拍。
- **FR-007**：问题分类必须固定为算法底座、终端采集、业务流程三类，并要求写证据来源。
- **FR-008**：必须同步 `specs/README.md`、`docs/02_product/02_quarterly_plan.md`、`docs/01_document_index.md` 和 agent 当前计划指针。
- **FR-009**：必须保留 V2.4 的最小边界：默认不新增 API、环境变量、数据库表或业务逻辑。
- **FR-010**：必须给出手工验收命令和静态检查命令，确保后续 `/goal` 可执行。
- **FR-011**：必须说明原生 spec-kit 脚本的分支要求；在 `main` 分支执行时，应创建或切换到 `025-wms-capture-loop-baseline` 分支，或让 `/goal` 使用显式路径执行，不依赖前置脚本。
- **FR-012**：必须说明 Face API 与 WMS 的 API Key 对齐检查；WMS 当前通过 Electron 主进程注入 `FACE_API_KEY` 并用同一个值发送 `x-api-key`。

## 关键实体

- **联动验收记录**：一次 Face API + WMS 现场验收的记录，包含环境、样例、结果、证据、结论和下一轮改进项。
- **WMS 终端 runbook**：WMS 开发者或现场人员执行摄像头、登录、日志回收和问题归因的步骤文档。
- **样例记录**：单次真人、翻拍、多人或模糊测试样例的结果行。
- **问题分类**：基于证据把问题归到算法底座、终端采集或业务流程。

## 成功标准

- **SC-001**：新同事从 `specs/README.md` 能在 1 分钟内找到 V2.4 的 roadmap、spec、plan 和 tasks。
- **SC-002**：验收人员只看 Face API 联动模板，就能填写一次完整联动验收记录。
- **SC-003**：WMS 开发者只看 WMS runbook，就能完成启动、摄像头检查、Face API 连通检查和日志证据收集。
- **SC-004**：每个失败样例都能在模板中归到算法底座、终端采集或业务流程，且必须填写证据来源。
- **SC-005**：所有新增文档不包含原图、视频、embedding、API Key 或真实用户敏感信息。
- **SC-006**：`git diff --check` 通过；文档未完成标记扫描无输出。
- **SC-007**：原生 spec-kit 与 `/goal` 两种执行方式都有清晰入口，不会因为当前在 `main` 分支而误判为规格缺失。
- **SC-008**：现场联调时能确认 Face API 端 `FACE_API_KEY` 与 WMS 请求头 `x-api-key` 来源一致。
