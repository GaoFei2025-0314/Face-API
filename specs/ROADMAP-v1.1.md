```text
face_api Roadmap v1.1
```

后续使用 `/goal` 推进 V1.1 时，以本文档作为范围和执行顺序依据。

## 2. 产品方向

Roadmap v1.0 已经让服务更适合本地 Windows 工作站运行，也更容易诊断、交付和恢复。

Roadmap v1.1 的方向，是把产品从“稳定的本地 API”推进到“更适合现场使用的人脸识别能力底座”，同时继续保持原来的产品边界：

1. 服务仍然是本地 REST API，不做完整业务平台。
2. 账号、权限、session、业务决策仍然由业务系统负责。
3. 本服务提供稳定的人脸识别能力、运维诊断能力和接入支持。
4. 新能力必须有清晰配置、可观测状态或运维控制。

V1.1 的主定位已确认：**现场安全可用版**。优先保证真实现场的安全 login、活体、防冒用、terminal 可追踪和运维可控，再做规模化搜索与管理增强。

## 3. 执行顺序

按以下顺序执行：

| 顺序 | Spec | 阶段 | 原因 |
|---:|---|---|---|
| 1 | `specs/009-liveness-anti-spoofing` | 活体与防冒用 | 先降低照片、屏幕、视频重放通过识别的风险 |
| 2 | `specs/010-recognition-policy-tuning` | 识别策略调参 | 让阈值和质量策略可度量、可解释、可调整 |
| 3 | `specs/011-vector-search-scaling` | 向量搜索扩展 | 在行为和指标清楚后，再支持更大人脸库 |
| 4 | `specs/012-admin-ops-console` | 运维管理控制台 | 给非开发运维人员提供安全可视化和基础管理能力 |
| 5 | `specs/013-terminal-integration-kit` | 终端接入规范包 | 统一多终端和业务系统的接入方式 |

除非用户明确修改本路线图，否则 V1.1 不实现完整 Web 平台、用户账号系统、token/session 发放系统或集中式多租户服务。

## 4. 每个阶段的标准流程

每个阶段都必须按以下顺序推进：

```text
spec -> clarify -> plan -> tasks -> implement -> verify -> document
```

每个阶段要求：

1. 从对应阶段的 `spec.md` 开始。
2. 先做澄清，处理未决问题。
3. 再写实施计划。
4. 拆成可执行任务。
5. 只实现当前阶段，不混入其他阶段。
6. 运行测试或明确的验证命令。
7. 同步更新相关文档。
8. 每个阶段单独提交，避免多个阶段混在一个提交中。

后续 `/goal` 建议一次只执行一个阶段。

## 5. 阶段详情

### 5.1 阶段 009 - 活体与防冒用

Spec：

- `specs/009-liveness-anti-spoofing/spec.md`

目标：

- 降低打印照片、屏幕照片、视频重放通过识别的风险。

主要产出：

- login 和注册都可分别配置是否要求活体；login 默认开启，注册默认关闭。
- 活体检测采用两阶段：先做单张图片判断，不确定时再进入动作挑战。
- 动作挑战使用 challenge 会话，前端通过摄像头提交连续图片帧。
- 第一版动作挑战至少稳定支持眨眼，动作类型结构预留摇头和张嘴。
- 清晰的活体通过/失败原因。
- 运维人员可见的活体模式和策略。
- 文档说明已覆盖的攻击类型，以及仍然不覆盖的范围。

已确认决策：

1. 前端主要接摄像头，活体采用“单张图片判断 + 不确定时动作挑战”的两阶段模式。
2. login 和注册都支持独立配置是否启用活体。
3. 某流程开启活体后，活体不通过或缺少有效 `challenge_id` 就拒绝。
4. 动作挑战通过 `challenge_id` 关联 login/注册，一次性使用，不可复用。
5. `challenge` 有效期 60 秒，动作完成窗口 10 秒。
6. 眨眼挑战一次提交 10 到 30 帧连续图片。
7. 用户端活体失败提示使用简短操作提示，详细原因进入 audit/log。

完成标准：

- login 和注册都可以配置为必须通过活体。
- 活体失败返回清晰中文原因。
- 运维人员可以确认当前是否启用了活体。

### 5.2 阶段 010 - 识别策略调参

Spec：

- `specs/010-recognition-policy-tuning/spec.md`

目标：

- 让阈值、质量、匹配决策在真实现场条件下可度量、可调整，并且更安全。

主要产出：

- 识别策略档案概念。
- 更清晰的阈值建议流程。
- 运维人员能读懂的 false accept / false reject 取舍说明。
- 基于 audit 的调参报告。

已确认决策：

1. 识别策略档案按 terminal 绑定。
2. V1.1 只展示调参建议，不自动修改阈值。
3. 阈值调整必须由人工确认后再改配置。

完成标准：

- 运维人员可以理解当前阈值和质量策略。
- login audit 数据可以支撑阈值调整判断。
- 策略变更有文档、有验证方法。

### 5.3 阶段 011 - 向量搜索扩展

Spec：

- `specs/011-vector-search-scaling/spec.md`

目标：

- 支持更大人脸库，并用实测性能和清晰扩展路径指导实现。

主要产出：

- 基准测试（benchmark）目标规模为 5 万人脸记录。
- 5 万人脸记录下 login/search 目标为 1 秒内返回。
- 可选 vector index 模式。
- index 新鲜度和重建状态可见。
- 保留回退到当前精确搜索的路径。

已确认决策：

1. V1.1 按 5 万人脸记录设计。
2. 默认精确搜索。
3. 只有 benchmark 证明 5 万规模达不到 1 秒目标时，才把近似搜索作为可配置模式。

完成标准：

- 搜索优化前后都有基准测试。
- 运维人员能看到 search index/cache 是否就绪。
- 注册/删除后搜索结果保持新鲜。

### 5.4 阶段 012 - 运维管理控制台

Spec：

- `specs/012-admin-ops-console/spec.md`

目标：

- 给非开发运维人员提供一个小型本地界面，用于查看状态、人脸记录、audit 和维护动作。

主要产出：

- 状态和配置视图。
- 人脸记录列表和查询视图。
- login audit 过滤视图。
- 支持删除人脸记录、备份数据库、恢复数据库。
- 不暴露 embedding 的安全操作。

已确认决策：

1. 控制台第一版包含只读查看、删除、备份和恢复。
2. 控制台授权复用现有 `FACE_API_KEY`。
3. 删除和恢复都必须有二次确认。
4. 数据库恢复必须先进入维护模式，再二次确认。

完成标准：

- 非开发人员不依赖 Swagger 也能查看健康、人脸记录和 audit 状态。
- 敏感数据仍然隐藏。
- 危险动作有清晰边界。

### 5.5 阶段 013 - 终端接入规范包

Spec：

- `specs/013-terminal-integration-kit/spec.md`

目标：

- 统一门禁 terminal、考勤 terminal 或其他业务客户端接入本地人脸 API 的方式。

主要产出：

- terminal identity 和命名规范。
- 标准 login/register/search 示例。
- retry 和 timeout 指引。
- 业务系统主动调用 face_api 的接入模式。
- 面向业务系统开发者的交付检查清单。

已确认决策：

1. 注册和 login 都必须带 `terminal_id`。
2. 业务系统主动调用 face_api；face_api 只返回识别、活体和失败原因结果。
3. face_api 不主动 callback 业务系统。

完成标准：

- 业务系统开发者可以按文档完成注册和 face login 接入。
- terminal ID 在日志和 audit 中保持一致。
- 接入错误能映射到清晰的用户/运维处理动作。

## 6. Roadmap v1.1 明确暂缓内容

除非用户明确修改本路线图，以下内容仍不进入 V1.1：

- 完整用户账号管理。
- 业务权限判断。
- token、session 或 refresh-token 发放。
- 多工作站云同步。
- 多租户 SaaS 管理。
- 移动端 App 开发。
- 完整企业 RBAC。
- 替代业务系统用户库。
