# 功能规格：业务接入 Demo 套件

**功能目录**：`021-business-integration-demo`

**创建时间**：2026-06-15

**状态**：已完成

**输入**：用户确认：“V2.0 采用业务接入 demo 套件；同时规划 Web 业务系统链路和受控终端链路；demo 用 FastAPI + SQLite；真实环境是 Java / Spring Boot；登录态用最小 JWT；终端 demo 同时提供页面和命令行脚本；不新增 face_api 公开接口。”

## 用户场景与测试 *(必填)*

### 用户故事 1 - 业务人员完成用户人脸绑定、解绑和换脸（优先级：P1）

业务人员需要先在业务系统中选择或新增用户，再为该用户绑定一张人脸，并能在后续解绑或换脸。

**优先原因**：正式业务系统必须保持“先有业务用户，再绑定人脸”的边界，避免 `face_api` 变成用户系统。绑定关系也是后续 Web 登录和终端登录的前置基础。

**独立测试**：在业务 demo 页面新增用户，绑定人脸，确认绑定记录；执行解绑后登录失败；重新绑定后登录恢复成功。

**验收场景**：

1. **假如** 业务用户未绑定人脸，**当** 业务人员采集单人脸图片并提交绑定，**那么** 系统保存 `user_id` 和 `face_id` 的一对一绑定。
2. **假如** 业务用户已经绑定人脸，**当** 业务人员再次绑定，**那么** 系统提示先解绑或执行换脸。
3. **假如** 业务人员执行换脸，**当** 新图片注册成功并完成绑定切换，**那么** 业务用户只保留一个有效绑定，旧 `face_id` 被清理或记录为待清理。
4. **假如** 绑定活体配置开启，**当** 业务人员绑定人脸，**那么** 绑定流程必须先完成 register challenge。

---

### 用户故事 2 - 业务后端代理完成 Web 人脸登录（优先级：P1）

业务系统开发者需要一个可运行 demo，证明浏览器不直接持有 `face_api` 的 `X-API-Key`，而是通过业务后端完成活体、人脸登录、业务用户校验和 demo JWT 签发。

**优先原因**：这是正式 Web 业务系统接入的安全基础，能避免把 `X-API-Key` 暴露给普通浏览器。

**独立测试**：启动 `face_api` 和 `business-demo`，打开 `http://localhost:8010`，选择已绑定且启用的业务用户，完成活体和人脸登录，页面显示 demo JWT 和业务用户信息。

**验收场景**：

1. **假如** 业务用户已存在且已绑定人脸，**当** 用户在业务 demo 页面完成人脸登录，**那么** 页面显示登录成功、业务用户信息和 demo JWT。
2. **假如** 浏览器打开开发者工具，**当** 执行 Web 登录流程，**那么** 浏览器请求中不出现 `face_api` 的 `X-API-Key`。
3. **假如** 业务用户已禁用或未绑定人脸，**当** 用户尝试登录，**那么** 页面显示业务层中文失败原因并写入业务 audit。

---

### 用户故事 3 - 受控终端完成识别并上报业务登录事件（优先级：P2）

终端开发者需要一个页面 demo 和一个命令行 demo，模拟一体机、闸机或 Windows 客户端直接调用 `face_api`，再把识别结果上报给业务后端。

**优先原因**：现场终端经常不是普通 Web 浏览器，V2.0 需要说明受控终端如何安全地持有 `X-API-Key` 并和业务系统衔接。

**独立测试**：打开终端页面或运行终端脚本，完成活体和 face login，拿到 `matched_user_id` 后上报 `business-demo`，业务 demo 记录 terminal 来源 audit。

**验收场景**：

1. **假如** 终端页面或脚本已配置 `X-API-Key` 和固定 `terminal_id`，**当** 终端调用 `face_api` 登录成功，**那么** 终端能把识别结果上报给业务后端。
2. **假如** 上报的 `user_id` 在业务系统中不存在或被禁用，**当** 业务后端处理终端事件，**那么** 返回业务拒绝原因并写入 audit。
3. **假如** 终端调用 `face_api` 失败，**当** 错误返回到终端 demo，**那么** 终端能显示中文原因而不是只显示 HTTP 错误。

---

### 用户故事 4 - Java / Spring Boot 团队按接入说明替换 mock 后端（优先级：P2）

真实业务后端团队需要文档说明如何在 Java / Spring Boot 中复刻 `business-demo` 的接入流程。

**优先原因**：V2.0 demo 用 FastAPI 是为了快速验证，但真实生产后端是 Java，必须避免 demo 和真实接入之间断层。

**独立测试**：Java 开发者阅读文档后，能说清 Controller、Service、`face_api` client、绑定表、业务 audit 和 JWT/session 的职责边界。

**验收场景**：

1. **假如** Java 团队阅读接入说明，**当** 设计自己的 Controller 和 Service，**那么** 能找到对应伪代码和请求字段说明。
2. **假如** Java 团队已有自己的 session/JWT/SSO，**当** 替换 demo JWT，**那么** 不需要修改 `face_api`。

### 边界情况

- `face_api` 未启动或 API 地址配置错误。
- `business-demo` 未配置正确的 `FACE_API_KEY`。
- 浏览器拒绝摄像头权限。
- 绑定图片没有人脸、多个人脸或质量过低。
- 用户已绑定人脸但再次绑定。
- 换脸过程中旧记录清理、新记录注册或绑定切换任一步失败。
- 登录 challenge 过期、失败或被重复使用。
- `face_api` 返回匹配成功，但业务用户不存在、禁用或绑定记录不一致。
- 终端上报重复事件或上报过期识别结果。

## 需求 *(必填)*

### 功能需求

- **FR-001**：必须新增独立 `business-demo` 规划，运行端口为 `8010`，不得把业务 demo 路由放入 `face_api` 主服务。
- **FR-002**：`business-demo` 必须维护自己的业务用户、绑定关系和业务登录 audit。
- **FR-003**：业务用户必须先存在，才能绑定人脸。
- **FR-004**：一个业务用户同一时间只能有一个有效人脸绑定。
- **FR-005**：必须支持绑定、解绑和换脸流程。
- **FR-006**：Web 人脸登录必须由 `business-demo` 服务端调用 `face_api`，浏览器不得直接持有 `face_api` 的 `X-API-Key`。
- **FR-007**：Web 登录必须走 login 活体 challenge。
- **FR-008**：绑定是否要求活体必须通过 `business-demo` 配置项控制，建议配置名为 `BUSINESS_DEMO_BINDING_LIVENESS_REQUIRED`，默认关闭，并在文档中说明正式现场可开启。
- **FR-009**：登录成功后，`business-demo` 必须签发 demo JWT 或等价的 demo 登录凭证。
- **FR-010**：登录失败时，页面必须显示中文原因，并同时记录业务 audit。
- **FR-011**：终端 demo 必须同时提供页面模式和命令行脚本模式，支持受控终端直接调用 `face_api` 后上报业务登录事件。
- **FR-012**：终端 demo 必须使用稳定 `terminal_id`。
- **FR-013**：V2.0 不得新增或改变 `face_api` 公开接口。
- **FR-014**：必须提供 Java / Spring Boot 接入伪代码，覆盖 Controller、Service、`face_api` client、绑定关系和业务 audit。
- **FR-015**：必须提供后续实现任务清单，保证可用 `/goal` 分阶段实施。
- **FR-016**：必须为 `business-demo` 自己的 API 提供请求/响应契约，避免后续实现自由发挥字段。
- **FR-017**：必须提供静态检查或测试，验证普通浏览器页面不包含 `face_api` 的 `X-API-Key`、`FACE_API_KEY` 或等价密钥变量。

### Key Entities

- **业务用户**：真实业务系统中的用户记录，包含 `user_id`、姓名、部门、状态等信息。
- **人脸绑定**：业务用户和 `face_api face_id` 的一对一有效绑定。
- **业务登录 audit**：业务系统维度的登录记录，记录来源、终端、成功失败、失败原因、相似度和 token 标识。
- **终端登录事件**：受控终端完成识别后上报给业务后端的事件。
- **Demo JWT**：V2.0 demo 用来模拟真实业务登录态的最小凭证。

## 假设

- 真实业务后端主要是 Java / Spring Boot，但 V2.0 demo 使用 FastAPI 降低当前项目实现成本。
- 业务系统已经或可以先创建业务用户，再做人脸绑定。
- 受控终端部署在可信内网环境，由项目方管理配置和密钥。
- Demo JWT 只用于演示，不代表生产登录安全方案；实现时优先用 Python 标准库 HMAC 生成 demo token，避免为演示 token 额外增加依赖。
- V2.0 继续使用本地 Windows 工作站和 SQLite 作为默认演示环境。
