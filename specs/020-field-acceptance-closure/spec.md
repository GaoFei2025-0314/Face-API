# 功能规格：现场验收收口与 P1/P2 小修

**功能分支**：`020-field-acceptance-closure`

**创建时间**：2026-06-14

**状态**：已完成

**输入**：用户确认：“V1.9 方向为现场验收收口；允许修复验收发现的 P1/P2 小问题，但不新增大功能。”

**现状说明**：V1.8 已完成文档基线、可维护性拆分、现场验收页面、运行状态总览和交互式架构图。V1.9 不再扩大功能面，而是把这些能力放到真实工作站和真实摄像头链路中做一轮收口验收。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 交付人员完成 Windows 工作站运行验收（优先级：P1）

交付人员需要确认服务能在目标 Windows 工作站上启动、停止、监控，并能通过健康检查判断服务是否可用。

**优先原因**：服务不能稳定启动和被监控时，后续摄像头、登录和业务接入验收都没有基础。

**独立测试**：在目标工作站运行启动入口，验证 `/health`、`/system/status` 和 `/config/effective`，并按 runbook 执行停止或监控检查。

**验收场景**：

1. **假如** 工作站已安装依赖并配置 API Key，**当** 交付人员启动服务，**那么** `/health` 返回可用状态。
2. **假如** 服务已启动，**当** 交付人员查看 `/system/status`，**那么** 能看到推理设备、模型、人脸库数量、鉴权和维护模式。
3. **假如** 服务需要停止或排障，**当** 交付人员按 runbook 操作，**那么** 能找到停止方式、日志位置和常见排障入口。

---

### 用户故事 2 - 现场人员完成摄像头注册登录闭环（优先级：P1）

现场人员需要用 `camera-integration.html` 完成摄像头授权、注册、login challenge 和 face login，并能看到中文结果。

**优先原因**：摄像头闭环是 face_api 是否能进入现场试用的核心证据。

**独立测试**：打开 `camera-integration.html`，配置 API 地址和 API Key，完成一次注册和一次登录；再触发至少一个失败场景，确认中文原因可见。

**验收场景**：

1. **假如** 摄像头授权成功，**当** 用户注册人脸，**那么** 页面显示注册成功或可理解的中文失败原因。
2. **假如** 登录活体配置开启，**当** 用户完成 challenge 后登录，**那么** 页面能调用 face login 并显示结果。
3. **假如** 登录失败，**当** 页面展示错误，**那么** 现场人员能看到 `message` 和中文 `reason`。

---

### 用户故事 3 - 项目负责人完成文档和架构一致性验收（优先级：P2）

项目负责人需要确认 PRD、季度计划、specs、runbook、API 文档和 `architecture.html` 与当前项目实际行为一致。

**优先原因**：文档和实际行为不一致时，后续交接、培训和 `/goal` 实施会重复踩坑。

**独立测试**：按 `docs/01_document_index.md` 的角色入口阅读文档，并抽查启动方式、接口说明、运行状态、摄像头验收和架构图。

**验收场景**：

1. **假如** 新同事只看文档入口，**当** 他寻找启动、接入、架构或验收说明，**那么** 能找到唯一清晰入口。
2. **假如** 接口行为已变化，**当** 前端或运维查 API 文档，**那么** 文档不会描述过期字段或过期流程。
3. **假如** 用 `architecture.html` 给同事演示，**当** 切换角色视图或流程播放，**那么** 页面内容与当前模块边界一致。

### 边界情况

- 工作站没有正确配置 Python 环境。
- 端口被占用。
- `FACE_API_KEY` 未配置或输入错误。
- 摄像头不存在、被占用或未授权。
- 活体 challenge 过期或失败。
- 人脸库为空。
- 备份目录不存在或恢复前未进入维护模式。
- 文档描述与接口实际行为不一致。
- 验收中发现的问题属于 P3/P4 或新功能诉求。

## 需求 *(必填)*

### 功能需求

- **FR-001**：必须记录 Windows 工作站启动、健康检查、状态查看和停止方式的验收结果。
- **FR-002**：必须记录 `camera-integration.html` 注册、login challenge、face login 和中文错误展示的验收结果。
- **FR-003**：必须记录最近 login audit 是否能解释登录成功和失败。
- **FR-004**：必须记录维护模式、备份和恢复流程的验收结果。
- **FR-005**：必须检查 `architecture.html` 与当前模块边界、接口入口和运维流程是否一致。
- **FR-006**：验收中确认的 P1/P2 问题必须先有复现步骤，再做最小修复。
- **FR-007**：涉及生产代码的小修必须优先补回归测试；无法自动化的页面或现场问题必须写入验收记录。
- **FR-008**：P3/P4 问题不得在 V1.9 临时扩范围，只记录为后续 backlog。
- **FR-009**：不得新增公开 API、环境变量、鉴权机制或大型前端项目。
- **FR-010**：接口、启动方式、错误码、页面入口或架构说明发生变化时，必须同步更新相关文档。

### Key Entities

- **现场验收记录**：记录 V1.9 每项验收结果、证据、残余风险和小修闭环。
- **P1/P2 小修**：由验收暴露、可复现、影响启动/登录/运维/文档准确性的最小修复。
- **摄像头闭环**：摄像头授权、注册、活体 challenge、face login 和 audit。
- **文档一致性**：PRD、季度计划、specs、runbook、API 文档和架构图与实际行为一致。

## 成功标准 *(必填)*

### 可衡量结果

- **SC-001**：现场验收记录覆盖启动、健康检查、状态、摄像头注册登录、中文错误、audit、备份恢复和架构图。
- **SC-002**：验收发现的 P1/P2 问题全部修复或明确记录为无法在当前环境验证的残余风险。
- **SC-003**：所有生产代码小修都有自动化测试或明确的手工复现记录。
- **SC-004**：全量单元测试通过。
- **SC-005**：本地 HTML 外部依赖扫描无新增外部脚本、样式、`import` 或 `require`。
- **SC-006**：季度计划、specs 索引和验收记录都指向 V1.9 当前状态。

## 假设

- V1.9 继续使用当前 Windows 工作站、本地 HTML 页面和 FastAPI 服务形态。
- `camera-integration.html` 仍是摄像头闭环验收入口。
- `admin.html` 仍是运维概览、维护模式、备份和恢复入口。
- P1/P2 小修不改变产品边界。
- 正式业务前端仍建议通过业务后端代理调用 face_api。
