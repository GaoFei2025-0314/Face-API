# 功能规格：识别安全与准确率增强

**功能分支**：`015-recognition-security-accuracy`

**创建时间**：2026-06-05

**状态**：草案

**输入**：用户描述：“后续版本要提升识别安全和准确率，包括更强活体、质量评分、误识别/拒识分析、阈值策略和人工复核建议。”

## 用户场景与测试 *(必填)*

### 用户故事 1 - 运维人员理解识别失败原因（优先级：P1）

运维人员需要知道一次 login 失败是因为无人脸、多脸、质量差、活体失败、相似度不足，还是底库记录异常。

**优先原因**：只有失败原因清楚，现场才能减少误判和重复调参。

**独立测试**：构造不同失败样本后，系统返回可区分的失败码，并在 audit 中记录原因。

**验收场景**：

1. **假如** 图片质量太差，**当** 执行 login 或注册，**那么** 系统返回质量相关失败原因。
2. **假如** 活体失败，**当** 执行 login，**那么** 系统记录活体失败，而不是只显示未匹配。
3. **假如** 相似度低于阈值，**当** 执行 login，**那么** 系统返回未匹配并记录相似度。

---

### 用户故事 2 - 运维人员调优识别策略（优先级：P1）

运维人员需要基于 audit 数据理解 false accept / false reject 风险，并安全调整 terminal 策略。

**优先原因**：不同摄像头、光照和安装角度会导致阈值策略不同。

**独立测试**：用一组 audit 样本生成调参建议，人工确认后能得到清晰的配置变更建议。

**验收场景**：

1. **假如** 某 terminal 拒识率偏高，**当** 查看调参报告，**那么** 报告解释可能原因并给出保守建议。
2. **假如** 样本不足，**当** 请求调参建议，**那么** 系统提示样本不足，不建议调整。

---

### 用户故事 3 - 安全负责人评估活体能力边界（优先级：P2）

安全负责人需要知道当前活体能防什么、不能防什么，以及是否需要升级到更强模型或硬件。

**优先原因**：不能把基础活体误认为企业级反欺骗能力。

**独立测试**：查看活体能力说明和测试样本报告，能区分已覆盖和未覆盖攻击类型。

**验收场景**：

1. **假如** 使用照片、屏幕、视频等样本测试，**当** 查看测试报告，**那么** 报告列出各类样本结果。
2. **假如** 现场风险等级更高，**当** 查看能力边界，**那么** 文档明确建议更强活体模型或硬件。

### 边界情况

- 光照极暗或过曝。
- 侧脸、遮挡、口罩、眼镜反光。
- 同一人多次注册。
- 双胞胎或高度相似人脸。
- 摄像头画面延迟或帧重复。
- 活体通过但最终匹配失败。
- 低质量底库照片导致 false reject。

## 需求 *(必填)*

### 功能需求

- **FR-001**：必须为 login 和注册输出更细的质量、活体、匹配和底库失败原因。
- **FR-002**：必须为人脸图片计算可解释质量指标，如检测置信度、脸框大小、亮度、清晰度或姿态。
- **FR-003**：必须提供 terminal 级识别策略配置说明和只读策略摘要。
- **FR-004**：必须基于 audit 生成调参建议，并明确样本不足时不建议调整。
- **FR-005**：必须记录相似度、阈值、质量指标、活体结果和 terminal 信息，便于后续分析。
- **FR-006**：必须文档化当前活体能力边界，避免过度承诺。
- **FR-007**：必须支持人工复核建议，而不是自动降低安全阈值。
- **FR-008**：必须保留保守默认策略，避免为了通过率牺牲安全。

### Key Entities

- **质量评分**：对输入图片可识别性的多维评估。
- **识别策略**：terminal 绑定的阈值、质量门槛和失败处理规则。
- **调参报告**：基于 audit 样本生成的建议和风险说明。
- **活体能力边界**：当前能力覆盖和不覆盖的攻击类型说明。

## 成功标准 *(必填)*

### 可衡量结果

- **SC-001**：100% login 失败都能归类到明确失败原因。
- **SC-002**：调参报告在样本不足时 100% 给出“不建议调整”的提示。
- **SC-003**：运维人员能在 5 分钟内判断某 terminal 是否因质量、活体或阈值导致失败。
- **SC-004**：默认策略不会自动降低阈值或绕过活体。
- **SC-005**：文档明确列出当前活体不承诺覆盖的攻击类型。

## 假设

- 当前 InsightFace/ONNX Runtime 仍是核心识别能力。
- V1.4 不引入 PyTorch。
- 更强活体模型或硬件可作为后续扩展，不强制进入本阶段。
- 业务系统仍负责最终放行或拒绝业务动作。
