# 功能规格：轻量防翻拍阈值治理与中风险重试机制

**功能分支**：`024-lightweight-anti-spoof-governance`

**创建时间**：2026-06-17

**状态**：已完成，固定摄像头现场五类样例验收通过

**输入**：V2.2 现场验收报告显示真人正脸稳定通过，但打印照片、手机屏幕照片、电脑屏幕照片和手机播放眨眼视频存在低风险成功，需要在不增加重型活体体验的前提下治理轻量防翻拍策略。

## Clarifications

### Session 2026-06-17

- Q: V2.3 验收目标？ → A: 平衡推荐；真人至少 2/3 通过，翻拍样例必须失败或至少中/高风险，不能低风险静默成功。
- Q: 优化层级？ → A: 增强现有轻量评分逻辑，不新增复杂动作，不引入重型模型。
- Q: 中风险如何处理？ → A: 默认不直接通过，提示用户重试一次。
- Q: 谁来强制中风险策略？ → A: 配置可切换，默认后端强制。
- Q: 中风险最多重试几次？ → A: 1 次；第二次仍中风险则失败或进入复核。
- Q: 后端如何判断是否已经重试过？ → A: 使用后端生成的 `risk_retry_token`。第一次中风险由后端返回一次性 token；第二次 login 必须携带该 token，后端校验 token 绑定、过期和使用状态，不依赖前端 `state` 或业务端自行计数。
- Q: 中风险重试错误如何返回？ → A: 默认返回 HTTP 403，`detail.code=ANTI_SPOOF_MEDIUM_RETRY_REQUIRED`，并固定携带 `detail.retry.risk_retry_token`、`detail.retry.expires_at`、`detail.retry.remaining_attempts`。客户端只透传 `risk_retry_token`，不得解析 token 内容。

## 范围边界

V2.3 只治理现有轻量防翻拍风险评分、中风险处理策略、页面提示、报告语义和接入文档。不新增业务用户系统，不新增完整风控平台，不承诺企业级强活体。

## 用户场景与测试

### 用户故事 1 - 真人用户仍能顺利登录（P1）

现场真人用户需要在当前摄像头登录流程中完成活体和 face login，不因为 V2.3 变得频繁误拒。

**独立测试**：使用同一个测试用户完成真人正脸 3 次验收，至少 2 次成功，且失败原因可解释。

### 用户故事 2 - 翻拍样例不再低风险静默成功（P1）

验收人员需要确认打印照片、手机屏幕、电脑屏幕和播放视频样例不会被记录为低风险成功。

**独立测试**：使用 V2.2 的五类样例矩阵，每类 3 次；翻拍样例结果必须为失败、中风险或高风险，不得低风险成功。

### 用户故事 3 - 中风险用户获得一次重试机会（P1）

真实用户在光线或动作不足时可能触发中风险，需要系统给出一次清晰重试机会，而不是直接把体验做成强拦截。

**独立测试**：构造中风险结果，`/auth/face-login` 默认返回需要重试的中文错误；前端显示重试提示；第二次仍中风险时不无限重试。

**服务端约束**：第一次中风险响应必须由后端生成 `risk_retry_token`。token 只允许同一 `terminal_id`、同一 login 重试组使用一次，并且必须在有效期内使用。客户端传入的 `state` 只能用于追踪展示，不能作为重试次数依据。

**错误响应契约**：第一次中风险默认返回以下结构，后端测试必须断言字段存在和类型稳定：

```json
{
  "detail": {
    "code": "ANTI_SPOOF_MEDIUM_RETRY_REQUIRED",
    "message": "检测到中风险，请重试一次",
    "reason": "当前画面存在轻量防翻拍中风险，请重新面对摄像头完成一次采集",
    "retry": {
      "risk_retry_token": "<opaque-token>",
      "expires_at": "2026-06-17T12:00:00Z",
      "remaining_attempts": 1
    }
  }
}
```

`risk_retry_token` 是不透明令牌；`expires_at` 使用 UTC ISO 8601 字符串；`remaining_attempts` 表示本次响应后服务端还允许的中风险重试次数，V2.3 默认只能是 `1` 或 `0`。audit、JSON/CSV 报告和页面导出不得包含原始 token。

### 用户故事 4 - 运维能复核阈值治理效果（P2）

运维和开发需要从 audit、验收报告和配置文档中看到风险等级、风险原因、处理动作和当前配置，判断是否需要继续调参。

**独立测试**：查看 `/audit/login/recent`、`acceptance.html` 导出的 JSON/CSV 和接入文档，能区分低风险成功、中风险重试、高风险拦截和普通活体失败。

## 功能需求

- **FR-001**：系统必须增强现有轻量防翻拍评分逻辑，降低移动照片或移动屏幕被判为 `normal_motion` 的概率。
- **FR-002**：系统必须保留低风险真人登录的现有体验，不默认增加复杂动作。
- **FR-003**：系统必须支持中风险处理策略配置，默认策略为后端强制重试。
- **FR-004**：默认策略下，中风险不得返回登录成功，必须返回中文重试提示和固定 `detail.retry` 结构。
- **FR-005**：系统必须限制中风险重试最多 1 次；V2.3 不新增最大重试次数环境变量，避免现场过度配置。第二次仍中风险时失败或进入复核。
- **FR-006**：系统必须由后端生成和校验 `risk_retry_token`，token 必须一次性、短期有效，并绑定 `terminal_id` 与 login 重试组。
- **FR-007**：系统不得使用客户端传入的 `state`、前端本地变量或业务端自报次数作为“最多重试 1 次”的权威依据。
- **FR-008**：中风险和高风险都必须写入 login audit，包含风险等级、风险原因、处理动作、terminal 和 retry 状态。
- **FR-009**：`camera-integration.html` 必须展示中风险重试提示，不能让用户误以为服务卡住。
- **FR-010**：`acceptance.html` 必须在报告中区分低风险成功、中风险重试、高风险和普通失败。
- **FR-011**：V2.3 必须保留 V2.2 报告隐私边界，不导出 API Key、原图、连续帧或 embedding。
- **FR-012**：文档必须说明 V2.3 是轻量治理，不承诺覆盖虚拟摄像头、深度伪造或专业攻击。
- **FR-013**：真实 Java / Spring Boot 接入说明必须明确默认策略下中风险不是登录成功，并且第二次重试必须回传后端签发的 `risk_retry_token`。
- **FR-014**：系统不得用单纯提高 similarity 阈值替代防翻拍治理。

## 成功标准

- **SC-001**：真人正脸 3 次验收至少 2 次成功。
- **SC-002**：打印照片 3 次验收不得出现低风险成功。
- **SC-003**：手机屏幕照片 3 次验收不得出现低风险成功。
- **SC-004**：电脑屏幕照片 3 次验收不得出现低风险成功。
- **SC-005**：手机播放眨眼视频 3 次验收不得出现低风险成功。
- **SC-006**：中风险默认返回重试提示，不返回 `authenticated: true`。
- **SC-007**：第二次仍中风险时不会无限重试。
- **SC-008**：audit 和验收报告能展示中风险原因和处理动作。
- **SC-009**：没有有效 `risk_retry_token` 的第二次请求不能绕过服务端重试限制。
- **SC-010**：全量 unittest、脚本 smoke、HTML 外部依赖扫描和 `git diff --check` 通过。

## 假设

- V2.2 导出的验收报告可作为 V2.3 的基线样例。
- 目标工作站仍是普通 Windows 摄像头场景。
- 业务系统仍由 Java / Spring Boot 或 `business-demo` 负责最终登录态。
- 现场允许用户在中风险时重试一次，但不接受复杂多动作流程。
