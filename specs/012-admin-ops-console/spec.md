# 功能规格：运维管理控制台

**功能分支**：`012-admin-ops-console`

**创建时间**：2026-06-05

**状态**：草案

**输入**：用户描述：“Roadmap v1.1 需要提供一个小型运维界面，用于查看状态、记录、audit 和维护操作。”

## Clarifications

### Session 2026-06-05

- Q: 运维管理控制台第一版权限范围是什么？ → A: 查看、删除、备份、恢复都包含。
- Q: 控制台登录/授权使用什么方式？ → A: 复用现有 `FACE_API_KEY`。
- Q: 数据库恢复如何控制风险？ → A: 必须进入维护模式，且二次确认后才能恢复。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 运维人员不依赖 Swagger 查看服务健康（优先级：P1）

非开发运维人员需要一个简单本地页面，用来查看服务状态、运行配置和识别就绪状态。

**优先原因**：Swagger 适合开发调试，但不适合日常工作站运维。

**独立测试**：运维人员打开控制台后，不看技术 API 文档也能确认健康状态、设备模式、数据库数量和鉴权状态。

**验收场景**：

1. **假如** 服务正在运行，**当** 运维人员打开控制台，**那么** 可以看到健康状态和关键运行状态。
2. **假如** 服务存在配置问题，**当** 运维人员打开控制台，**那么** 控制台显示清晰告警或诊断状态。

---

### 用户故事 2 - 运维人员安全查看和删除人脸记录（优先级：P1）

运维人员需要列出、查找和删除已注册人脸记录，但不能暴露 embedding 或内部敏感数据。

**优先原因**：运维人员需要确认注册状态并排查用户问题。

**独立测试**：运维人员可以按业务身份查询记录、二次确认后删除记录，并确认页面从不展示 embedding。

**验收场景**：

1. **假如** 已有用户注册，**当** 运维人员按用户身份搜索，**那么** 显示匹配的人脸记录但不显示 embedding。
2. **假如** 用户没有记录，**当** 运维人员搜索，**那么** 控制台明确显示未找到已注册人脸。
3. **假如** 运维人员要删除人脸记录，**当** 未完成二次确认，**那么** 删除不会执行。

---

### 用户故事 3 - 运维人员查看 login audit（优先级：P2）

运维人员需要按时间、成功状态、terminal 和失败原因查看最近 face login 尝试。

**优先原因**：现场 login 问题需要快速定位。

**独立测试**：运维人员可以过滤 audit 记录，并判断失败原因是无人脸、相似度低、活体失败还是配置问题。

**验收场景**：

1. **假如** 存在 login audit 记录，**当** 运维人员按失败状态和 terminal 过滤，**那么** 页面显示对应尝试及清晰原因。

---

### 用户故事 4 - 运维人员执行备份和恢复（优先级：P2）

运维人员需要在控制台中触发数据库备份，并在维护模式下执行数据库恢复。

**优先原因**：备份和恢复是现场交付后的关键运维动作，但恢复会覆盖当前数据，必须有保护。

**独立测试**：运维人员能完成备份；恢复必须先进入维护模式并二次确认，否则不会执行。

**验收场景**：

1. **假如** 服务处于正常运行状态，**当** 运维人员触发备份，**那么** 控制台显示备份结果和备份位置。
2. **假如** 服务未进入维护模式，**当** 运维人员尝试恢复数据库，**那么** 控制台拒绝恢复并提示先进入维护模式。
3. **假如** 服务已进入维护模式，**当** 运维人员二次确认恢复，**那么** 控制台执行恢复并提示后续健康检查。

### 边界情况

- API key 缺失或错误。
- 人脸库为空。
- audit 记录为空。
- 某个维护操作有危险，需要确认。
- 控制台从不可信来源打开。
- 运维人员尝试在非维护模式下恢复数据库。
- 备份或恢复过程中目标文件不可用。

## 需求 *(必填)*

### 功能需求

- **FR-001**：控制台必须显示服务健康和关键运行状态。
- **FR-002**：控制台必须展示人脸记录列表和查询结果，并隐藏 embedding。
- **FR-003**：控制台必须展示 login audit，并支持按成功状态和 terminal identity 过滤。
- **FR-004**：控制台展示受保护信息前，必须复用现有 `FACE_API_KEY` 做运维授权。
- **FR-005**：控制台必须清晰区分安全只读视图和有破坏性的维护动作。
- **FR-006**：控制台必须支持二次确认后删除人脸记录。
- **FR-007**：控制台必须支持触发数据库备份，并展示备份结果。
- **FR-008**：控制台必须支持数据库恢复，但恢复前必须进入维护模式并二次确认。
- **FR-009**：危险动作必须要求明确确认，并说明后果。
- **FR-010**：控制台必须链接或展示备份、恢复和排障指引。

### 关键实体

- **运维控制台**：用于查看服务状态和维护信息的本地界面。
- **人脸记录视图**：已注册人脸记录的安全展示形式。
- **audit 视图**：最近 login 尝试和失败原因的过滤展示。
- **维护模式**：阻止高风险恢复操作与正常请求并发执行的受控状态。
- **维护动作**：由运维人员触发、且后果明确受控的动作，包括删除、备份和恢复。

## 成功标准 *(必填)*

### 可度量结果

- **SC-001**：非开发运维人员能在 2 分钟内确认服务健康和记录数量。
- **SC-002**：100% 控制台记录视图隐藏 embedding 和 API secret。
- **SC-003**：运维人员能在 2 分钟内按成功状态和 terminal 过滤 login audit。
- **SC-004**：100% 删除和恢复操作在执行前必须经过二次确认。
- **SC-005**：100% 数据库恢复操作在非维护模式下被拒绝。

## 假设

- 控制台用于本地工作站运维，不是完整云管理平台。
- 业务系统仍然是用户账号和权限的真实来源。
- 控制台第一版包含查看、删除、备份和恢复；删除和恢复必须按高风险操作处理。
